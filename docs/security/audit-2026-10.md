# Security audit — Phase 11 (2026-10-25)

Scope: RLS policies, API authorization, input validation, file uploads, sensitive data exposure, secrets, cross-tenant access, rate limiting and audit logs. Method: code review plus automated checks (pgTAP `00_rls_coverage`, `03_security_hardening`; Vitest security suites; Playwright; `npm audit`). This is an internal engineering review, **not** a third-party penetration test. Commission one before launch.

## Automated evidence

- pgTAP (36 assertions):
  - every public table has RLS and a policy;
  - every SECURITY DEFINER function pins `search_path`;
  - anon can execute no definer function, and no policy targets `anon` or `public`;
  - server-only functions (verified payment events, delivery worker, jobs) are not executable by `authenticated`;
  - private tables grant API roles nothing;
  - audit, payment-event and stock histories are immutable;
  - document buckets are private;
  - money, audit, order and delivery tables can't be written directly;
  - every currency column is PHP-only.
- Vitest security suites:
  - cross-tenant reads and writes for households, organizations, workers, suppliers, payments and admins;
  - revoked access;
  - verification conflicts;
  - webhook signatures and replay;
  - concurrency;
  - signed-out API callers read nothing;
  - client bundles contain no server secrets.
- `npm audit`: 0 known vulnerabilities (production and dev dependencies).

## Sensitive data handling

- The service worker never intercepts Supabase or other origins and never stores page HTML (`pwa.spec.ts` asserts that caches contain only public static assets). Authenticated responses are rendered per request (`cacheComponents: false`).
- Exact addresses are released to providers only after a booking is confirmed, and to workers only for their assignments. Suppliers never see households.
- Payment card data never touches Bahay+ (provider-hosted checkout).
